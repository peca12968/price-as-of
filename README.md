# Page Ledger｜翻到下一頁時，帳本剛好多了兩筆

門市交班要逐頁核對收據。第一頁看到編號 4、3，這時收銀機送來一筆最新交易，另一台離線裝置也補送了一筆較早的交易。Page Ledger 讓這次核對繼續讀完起始時的明細，下次重新開啟時再看新增資料。

## 跑一次翻頁實驗

使用 Python 3.12 與 SQLite 3.37 以上，僅需標準函式庫。在專案目錄執行以下指令，示範會在暫存資料庫建立兩條獨立的讀寫連線。

```sh
python demo.py
python -m unittest -v
```

| 讀取時機 | 回傳的收據編號 |
| --- | --- |
| 原本四筆收據的第一頁 | 4、3 |
| 兩筆新資料提交後，用即時查詢跳過前兩列 | 3、2（重複看到 3） |
| 同一時間，用第一頁留下的游標讀取下一頁 | 2、1 |
| 重新開始，讀取目前所有資料 | 5、4、3、2、6、1 |

收據 6 是補送資料，交易時間比收據 2 早。游標保存首次查詢時已提交的最大流水號，因此即使後來交易的時間落在舊頁面之間，也只會出現在新一輪查詢。相同交易秒數以流水號由大到小排序。資料表拒絕更新、刪除、覆寫及插入舊流水號。新收據和流水號上限在同一筆交易提交。[分頁與資料表實作](ledger.py)

## 深頁面要做多少查詢工作？

示範另外建立 20,000 筆收據，每八筆共用一個交易秒數。在前一頁位置已知的條件下，兩種查詢取出排序後第 18,001 筆起的相同 21 筆（20 筆顯示、一筆判斷有無下頁）。

| 讀法 | 本機 SQLite 3.49.1 的 progress callback 次數 |
| --- | ---: |
| 依門市索引掃描，略過 18,000 筆 | 108,251 |
| 依門市、交易時間與流水號的複合索引續讀 | 425 |

兩者使用相同資料、排序、流水號上限與回傳欄位。程式逐筆比對結果，再列出 `EXPLAIN QUERY PLAN`。回呼間隔設為一個虛擬機指令，用於比較這兩個查詢的工作量。數字隨 SQLite 版本、資料分布與執行計畫而變，未量測使用者端延遲。測量只涵蓋續讀這一頁，任意跳到第 N 頁需要另行取得位置。[實驗程式](demo.py) · [SQLite 複合欄位分頁](https://www.sqlite.org/rowvalue.html#scrolling_window_queries) · [進度回呼規格](https://sqlite.org/c3ref/progress_handler.html)

## 在自己的範例帳本操作

```sh
python ledger.py init receipts.db
python ledger.py append receipts.db north 1700000000 3500
python ledger.py append receipts.db north 1700000000 -500
python ledger.py page receipts.db north --limit 1
```

在輸出中複製 `next` 的值，用 `python ledger.py page receipts.db north --after "游標值"` 續讀。交易時間使用 Unix 秒數，金額使用整數分，負數可表示退款。每頁可取 1 至 200 筆，最後一頁的 `next` 為 `null`。續讀時可改變每頁筆數，或在不同程序重播同一個游標。

游標包含格式版本、帳本識別、門市、流水號上限、最後一筆的排序鍵。工具會拒絕混用其他帳本或門市的游標。游標採可解碼的 Base64 表示，適用於可信任的本機工具。此設計以只增不改的收據為前提，歷史資料更正可另加一筆沖銷紀錄。

測試使用固定亂數種子建立 32 組歷史。每次翻頁間由另一條連線加入同門市與其他門市的資料，再與起始資料的獨立排序逐筆比較。另測同秒交易、退款、頁面大小變動、游標重播、交易回滾及 CLI 跨程序續讀。[整合測試](test_ledger.py) · [跨平台 CI](.github/workflows/ci.yml)
